# 3-Tier Memory System — Learnings

## Architecture Rules

1. **Tier 1 (MEMORY.md) is an index only** — never put growing content here, only links to Tier 2. Must stay under 200 lines.
2. **Tier 2 (_index files) coordinate, don't store** — they reference Tier 3 files. Keep each under 60 lines.
3. **Tier 3 is source of truth** — full content with frontmatter in typed folders.
4. **All 5 folders are mandatory** — sessions/, pendientes/, learnings/, plans/, research/ — even if empty.

## Dual-Write Rules

5. **Sessions, pendientes, and learnings ALWAYS dual-write** — Tier 2 index + Tier 3 detail file. No exceptions.
6. **Plans and research: SCAN for signals, don't skip** — detect plan mode (ExitPlanMode, plan files), web searches, comparisons, investigation keywords. Any signal → dual-write. The old "only if applicable" wording caused agents to always skip.
7. **On pendiente resolve**: remove from _pendientes.md, fill Resuelto + Sesion in monthly archive.
8. **_origen wikilink required** — every pendiente must link to its source session or plan.

## Bridge Rules (Model B)

9. **Bridge is redirect-only** — auto-memory MEMORY.md contains ONLY the bridge template. Zero inline content.
10. **Bridge uses relative paths** — `memory/...` not absolute paths. Portable across machines.
11. **Red flag**: auto-memory MEMORY.md with >20 lines of real content = broken bridge.

## Session Rules

12. **Register DURING execution, not at end** — batching = forgetting items.
13. **Checkpoints, not session close** — multiple checkpoints per session are fine. Each includes git commit.

## Plugin Distribution — CRITICAL LESSONS

14. **Marketplace = repo with .claude-plugin/marketplace.json** — plugin lives inside plugins/<name>/ subdirectory with its own .claude-plugin/plugin.json.
15. **plugin.json schema is strict** — `repository` must be string (NOT object), use `keywords` (NOT `tags`). Always validate with `claude plugin validate`.
16. **${CLAUDE_PLUGIN_ROOT}** — correct variable for hook commands in plugins. NOT $CLAUDE_PLUGIN_DIR.
17. **Local command names must use `-3t` suffix** — Generic names (checkpoint, status, audit) collide with global skills (e.g., gstack). All local commands use `-3t` suffix: /checkpoint-3t, /status-3t, /audit-3t, /backfill-3t. session-start.sh auto-migrates old names on first run after update.
18. **Marketplace cache is sticky** — `/plugin marketplace update` does NOT always pull latest. If stale, must do `cd ~/.claude/plugins/marketplaces/<name> && git pull` manually, or remove + re-add.
19. **`/plugin marketplace remove` + `add` may reuse stale clone** — doesn't guarantee a fresh clone. Manual git pull in the marketplace directory is the reliable fix.
20. **extraKnownMarketplaces only makes it known** — users still need to run `/plugin install` + `/reload-plugins`. It does NOT auto-install.
21. **Version bump forces cache refresh** — always bump version in plugin.json when pushing fixes, otherwise cached versions persist.
22. **README must not assume plugin knowledge** — step-by-step with one command per block, wait points between steps, troubleshooting for every known failure mode.
23. **Don't mix languages in user-facing text** — keep README and plugin description in one language. Spanish terms only in internal filenames (_pendientes.md).
24. **Index pruning is automatic** — checkpoint Step 5b trims session/plan/research indexes. Tier 3 detail files are NEVER deleted. Only index rows are removed after exceeding retention limits (10 sessions, 5 completed plans, 5 completed research). — ⊘ SUPERSEDED (2026-09-02, v2.12.0 Fase 2): la poda de sesiones/planes/research la hace `journal-compact.py` al aplicar cada evento, por fecha (Fecha; `_completado: FECHA_` en research); filas sin fecha nunca se podan; Step 5b solo limpia `- [x]`. Ver [[plans/plan-journal-concurrencia-v2.12.0]].
25. **Git commit is best-effort in checkpoint** — Step 6 detects git issues (not installed, no repo, user not configured, .gitignore) and skips gracefully. Memory file writes (Steps 1-5) are the valuable part; git commit is a convenience, never a blocker.
26. **Version bump is mandatory on every push** — Claude Code uses plugin.json version as cache key. Same version across two commits = skip update. ALWAYS bump version in plugin.json before pushing changes to the repo.
27. **Auto-update must be enabled automatically** — Third-party marketplaces don't auto-update by default (only official Anthropic marketplaces do). session-start.sh, setup-memory, and migrate all auto-enable `autoUpdate: true` in `known_marketplaces.json`. Never depend on user manual action for updates.
28. **`claude plugin` works as terminal CLI** — Not just REPL `/plugin`. Commands like `claude plugin marketplace add`, `claude plugin install`, `claude plugin list` all work from a regular shell. Terminal form is preferred in docs because AI agents universally understand shell commands but may not recognize REPL slash commands.
29. **README must be agent-readable** — AI agents guide most installations. Use HTML comments for agent-only instructions (invisible on GitHub), prefer terminal commands over REPL slash commands, always provide a manual fallback (git clone + settings.json).
61. **Secrets en `memory/` se redactan deterministamente, no se delegan al agente.** `/checkpoint-3t` y `/save-learning` hacen `git add memory/` + commit, así que en proyectos donde `memory/` NO está en `.gitignore`, un secret capturado verbatim en un digest se commitea y al push se filtra (caso real: un agente pusheó una carpeta de memoria con keys reales). Una regla de "acuérdate de redactar" es la fragilidad de #57/#24 otra vez → la garantía es `bin/scan-secrets.py`: detecta shapes de alta confianza (AKIA/ghp_/sk-/AIza/xox/sk_live_/JWT/PRIVATE KEY) + regla genérica `key=valor` con gate de entropía (no destroza prosa), reemplaza solo el VALOR por `<REDACTED>`, salta `$VAR`/`<REDACTED>`/placeholders (idempotente, atómico, nunca imprime el secret). Cableado en 3 capas: prevención (checkpoint Step 5d + save-learning Step 3c, `--apply` antes del commit), detección (audit + SessionStart, `--count` warning-only). CRÍTICO: la redacción protege commits futuros; una key ya pusheada está comprometida y DEBE rotarse — el historial no se des-filtra. Es #57 aplicada a secrets. v2.10.0.
60. **Encoding de ruta de proyecto = `[^A-Za-z0-9]→-`, NUNCA solo `/→-`.** Claude Code nombra la carpeta en `~/.claude/projects/` reemplazando **todo carácter no alfanumérico** por `-` (barras, espacios, puntos, guiones bajos; cada char individual → `/.paperclip` da `--paperclip` doble guión). El plugin usaba `sed 's|/|-|g'` (solo barras) inlineado en 19 sitios (`bin/`, `templates/`, `commands/`), así que cualquier proyecto con espacio/punto en la ruta (`…/Vecino Seguro/Panel PHP`) calculaba una carpeta inexistente y el índice de backfill/recall caía mal. Fix: `sed 's/[^A-Za-z0-9]/-/g'` en todos. Validado contra carpetas reales (`-Users-will-Projects-3-tier-memory`, `-Users-will--paperclip-…`). Rutas "limpias" (sin espacio/punto/`_`) dan el mismo resultado → no necesitan migración; comandos idempotentes → re-correr basta. Reportado por usuario en v2.9.3. Refuerza #26 (bump al cambiar). v2.9.4.
63. **`print()` con caracteres no-ASCII truena en Windows si no se fuerza UTF-8 en stdout.** `enrich-memory.py`, `ensure-frontmatter.py`, y `scan-secrets.py` imprimen `→`/`—`/`…` en su output; en Windows la codificación de `sys.stdout` sigue el codepage de la consola (cp1252 es default común), no UTF-8 — y esto pasa incluso vía command substitution (`$(python3 script.py)`), no solo en consola interactiva. Dos de los tres scripts corren automático en cada sesión (hook SessionStart), así que un usuario Windows lo pega sin hacer nada raro. Fix: `sys.stdout.reconfigure(encoding="utf-8")` al inicio de cada script (guardado con `hasattr`), independiente del locale del shell que invoque. No delegar a `PYTHONIOENCODING=utf-8` en el entorno — eso es un workaround del usuario, no cubre invocaciones internas del plugin (ej. el hook). Reportado por usuario en Windows que ya lo había parcheado localmente exportando esa variable. v2.10.0.

## Backfill Rules

30. **JSONL backfill is a separate command** — /backfill-3t is standalone, not embedded in setup or migrate. It's expensive (reads all JSONL, AI synthesis per session). Setup and migrate detect JSONL files and recommend /backfill-3t.
31. **Two-phase extraction pipeline** — Phase 1 (Python script) strips tool_results, thinking blocks, file-history-snapshots to produce a condensed digest. Phase 2 (Claude) reads the digest and synthesizes memory artifacts. This keeps token budget manageable even for 2.5MB JSONL files.
32. **Backfilled sessions use `status: backfilled`** — Distinguishes AI-reconstructed sessions from live-captured ones. Backfill pendientes are marked with `(backfill)` in _origen.
33. **Progress tracking via .backfill-progress.json** — Lives in the JSONL directory. Tracks processed/skipped UUIDs. Enables resume after interruption and idempotency on re-run.
34. **session-start.sh notifies about pending backfill** — Counts JSONL files vs processed, prints "BACKFILL PENDIENTE: N sesiones" if any remain.
35. **Global skills shadow local commands** — Claude Code resolves global skills (~/.claude/skills/) before local commands (.claude/commands/). If a global skill has the same name as a local command, the skill wins. This is why all local commands use the `-3t` suffix.
36. **session-start.sh must install missing commands, not just update** — Auto-update loop must check if template exists even when local file doesn't. Otherwise new commands added in plugin updates never get installed. Fixed in v2.2.1.
37. **Plugin skills don't appear in autocomplete** — Documented bug (anthropics/claude-code #18949, #21125, #41842). Plugin-distributed skills with namespace `plugin:skill` are invisible in `/` menu. This makes them impractical for frequently-used commands.
38. **Checkpoint needs conversation context** — checkpoint scans the entire conversation for pendientes, learnings, and session summary. Skills with `context: fork` run in isolated subagents without conversation history. Commands stay in-session — this is correct for checkpoint.
39. **Don't migrate commands to plugin skills** — Evaluated 2026-04-06. Three blockers: broken autocomplete, checkpoint needs conversation context, `-3t` suffix is more ergonomic than namespace. Re-evaluate when Anthropic fixes plugin skill autocomplete.
40. **$CLAUDE_PLUGIN_ROOT is NOT available in local commands** — Only set during hook execution (hooks.json commands). Markdown command templates in .claude/commands/ run as Claude instructions, not as hook subprocesses. Any command that references plugin binaries must use `find "$HOME/.claude/plugins" -name "script.py" -path "*/3-tier-memory/*"` as fallback. Fixed in v2.2.2.
41. **$CLAUDE_PROJECT_DIR is unreliable — always fallback to stdin `cwd`** — Despite official docs saying it's available in all command hooks, some environments don't set it. All hook scripts must source resolve-project-dir.sh which reads `cwd` from the hook's stdin JSON as fallback. Uses jq if available, python3 otherwise. Fixed in v2.2.3.
42. **Trivial = tiny AND no signal** — `extract-session-digest.py` marks a session trivial only when `line_count < 10 AND userMessageCount < 2 AND no signal`. Signals: any `signals.*`, plan permission mode, or any tool use. OR semantics were the original bug — a 163-line plan session with 2 user msgs was dropped. `BACKFILL_FORCE_ALL=1` disables the gate and moves `skipped[]` to `previously_skipped[]` for a full re-run. Thresholds overrideable via `BACKFILL_TRIVIAL_LINE_THRESHOLD` / `BACKFILL_TRIVIAL_USER_MSG_THRESHOLD`. Fixed in v2.4.0.

## Pendientes Lifecycle

43. **Inyecta contenido, no contadores** — SessionStart debe meter los pendientes abiertos *inline* en el contexto del agente, no solo un conteo. Sin el texto visible, el agente nunca cruza la peticion del usuario contra items abiertos y los resuelve sin marcarlos. Cap a 10 items, ordenados por prioridad luego por edad (mas viejos primero porque son los mas sospechosos de estar ya resueltos). Framing imperativo: "Antes de responder, verifica si la peticion se relaciona con...". v2.7.0.
44. **Reconciliacion antes de extraccion** — Checkpoint Step 3 debe enumerar y clasificar CADA pendiente existente (resolved/still-open/superseded/abandoned) ANTES de buscar nuevos. Con extraccion primero el agente entra en modo "nuevo trabajo" y la reconciliacion se vuelve un afterthought. El paso debe imprimir tabla de reconciliacion al usuario para comprometer la decision. v2.7.0.
45. **`_creado: YYYY-MM-DD` inline en cada pendiente** — Formato canonico: `- [ ] <texto> — _origen: [[sessions/...]]_ — _creado: YYYY-MM-DD_`. Habilita ordenamiento por edad en SessionStart y senales de staleness futuras. Parser de session-start.sh debe tolerar items legacy sin `_creado:` (van al final del bucket). Backfill usa la fecha de la sesion origen (`dateFirst`), no hoy. v2.7.0.

## Relevance Recall & Decay (v2.8.0)

46. **Recall por relevancia = hook UserPromptSubmit, no SessionStart.** La brecha #1 vs el nativo era que la memoria nunca se cruzaba contra el prompt. Solución: hook `UserPromptSubmit` (`bin/recall.sh`) que puntúa cada unidad de memoria contra el prompt e inyecta top 3-4. SessionStart sigue inyectando pendientes+conteo de reglas; recall añade la capa por-turno. Silencio si nada supera umbral — el ruido degrada más que la ausencia.
47. **Motor léxico puro (BM25-lite + IDF), cero dependencias.** `score = relevancia × recencia × importancia`. Relevancia = suma de IDF de términos del prompt que matchean keywords de la unidad (términos raros pesan más). Decisión deliberada de NO usar embeddings: mantiene el ethos portable/git-versioned/sin-deps. Límite conocido: cross-language (prompt ES vs learning EN no matchea) — aceptado.
48. **Índice de recall es cache DERIVADO, va fuera de memory/.** Vive en `~/.claude/projects/<encoded>/.recall-index.jsonl` junto a `.backfill-progress.json` (per-máquina, nunca commiteado). Se reconstruye cuando cualquier `.md` de memory/ es más nuevo que el índice (`find -newer`). ~70ms/turno. NUNCA tratar el índice como fuente de verdad: regenerable siempre desde los .md.
49. **Tokenización idéntica en builder y scorer.** `build-recall-index.py` y el python embebido de `recall.sh` deben tokenizar igual (mismas stopwords ES/EN, mismo regex). Tokens ≥3 chars OR longitud-2 con dígito (captura identificadores como `3t`, `v2`). Si divergen, el matching se rompe silenciosamente.
50. **importance/last_verified son OPCIONALES y retrocompatibles.** `importance: 0-10` (salience Generative-Agents) en frontmatter de sessions/learnings alimenta el ranking; ausencia → default 5. `last_verified: YYYY-MM-DD` en learnings habilita el flag de staleness de /audit-3t. Archivos legacy sin estos campos funcionan sin cambios — patrón de reglas #41/#45.
51. **Decay por tipo, no global.** Half-life en el scorer: sessions 30d, pendientes 60d, plans/research 180d, learnings 3650d (casi infinito — el conocimiento no caduca como una sesión). Pendientes >30d se marcan `⚠ posible stale` en SessionStart y se empujan a reconciliación (Step 3a).
52. **Consolidación = supersede, no overwrite.** `/consolidate-3t` resuelve contradicciones marcando la regla vieja con `⊘ SUPERSEDED by [[...]]` y conservándola (preserva el "por qué" histórico, patrón Zep/knowledge-graph temporal). Dedup y reflexión (sesiones→reglas de mayor nivel) también proponen antes de tocar. Nunca borra learnings en silencio.

## Scale (v2.9.0)

53. **El costo de gestión debe ser proporcional al HALLAZGO, no al tamaño del corpus.** Evidencia: `/consolidate-3t` v2.8.0 escaneaba a ciegas todo el corpus (O(n²) semántico) — en paperclip (284 learnings) gastó un fan-out multi-agente para encontrar ~1 dup real. Fix: pre-filtro determinista (`bin/find-dup-candidates.py`, Jaccard sobre tokens del recall index) surfacea solo los pares candidatos; los agentes juzgan ese set chico. Si nada supera el umbral → **early-exit "corpus limpio" sin gastar un agente**. 1349 units → 18 pares en <100ms. Patrón general: empuja el filtrado/selección a Python determinista, deja que los agentes juzguen un set pequeño. v2.9.0.
54. **Features nuevas necesitan un PATH DE BACKFILL para corpus pre-existentes.** `importance:` y `_creado:` solo se escribían en archivos NUEVOS → en paperclip 0/284 learnings y 0/294 sessions tenían importance, y 0 pendientes tenían `_creado:`. Resultado: recall corría degradado (todo salience=5, factor neutro en `imp/5`) y staleness era no-op total (sin `_creado` → `None` → nunca marca). Una feature opcional-hacia-adelante NO basta a escala; hace falta migración. Solución: `/enrich-3t` (`bin/enrich-memory.py`) rellena ambos campos en archivos existentes — dry-run, idempotente, atómico, nunca toca texto. v2.9.0.
55. **Heurísticas de importance deben DISCRIMINAR; un score alto uniforme es no-op.** Recall escala relevancia por `importance/5`, así que poner todas las sessions en 7 no cambia el ranking — equivale a dejarlas en 5. Lección: solo demotar lo trivial (sessions backfilled→3, sin artefacto durable→4) y dejar las sustanciales NEUTRAL (sin campo → default 5). El señal real de importance vive en learnings (half-life 3650d → es el ranking primario ahí). Y markers de scoring demasiado comunes (`gate`/`must` en un corpus de governance) aplanan el señal — usar markers fuertes/específicos. v2.9.0.
56. **Convención de archival + exclusión de scan.** `memory/archive/`, `*.bak`, `*.zip`, `*.archived.md`, `*-archived-*.md` se excluyen del índice de recall (`is_excluded()` en build-recall-index.py), del rebuild lazy (`recall.sh` `find -newer`), y de consolidate/audit (nota de skip). El clutter archivado NO debe contaminar recall ni inflar consolidación. La exclusión es path-based (segmento `archive/`) + extensión, regex compartido entre los scripts. v2.9.0.
57. **Garantías mecánicas NO se delegan al agente — se sellan deterministamente.** Los archivos Tier-3 los escribe el agente siguiendo checkpoint/save-learning; sin enforcement, a la larga algunos salen sin frontmatter (en paperclip: 34 learnings + ~36 plans/research/reference, todos creados por checkpoint) y corren degradados en silencio. Fix: `bin/ensure-frontmatter.py` antepone un bloque mínimo (type/date/status) a cualquier archivo tipado top-level que lo necesite — idempotente, atómico, nunca toca el body, solo structure (importance lo pone enrich). Enganchado en 3: prevención (paso final de checkpoint Step 5c + save-learning), detección (audit + warning SessionStart, sin mutar), reparación (enrich sella antes de puntuar). Scope = top-level (mismas unidades que indexa recall); `.md` anidados intactos. Es la regla #53/#55 aplicada al punto de escritura. v2.9.1.
58. **El aviso de checkpoint vivía solo del PreCompact del harness — rehén de su umbral.** El plugin NUNCA hardcodeó 200k; `pre-compact.sh` es un recordatorio fijo que reacciona al auto-compact de Claude Code, que dispara ~200k y NO escala a 1M (el harness solo da on/off vía `DISABLE_AUTO_COMPACT=1`, sin setting de umbral; PreCompact no recibe conteo de tokens). En 1M se sentía prematuro. Fix: `bin/context-nudge.sh` (hook UserPromptSubmit) lee el uso REAL del transcript (`usage.input_tokens + cache_read + cache_creation` del último mensaje, leyendo el tail del JSONL) y avisa a una fracción configurable de un window configurable (`THREET_CONTEXT_WINDOW` default 200k, `THREET_CHECKPOINT_RATIO` default 0.8). De-dupe por bucket de 10%. El transcript registra el modelo base SIN el sufijo `[1m]`, por eso el window es un knob, no auto-detectable. Reemplaza al PreCompact (que se pierde si desactivas auto-compact). v2.9.2.

59. **MEMORY.md (Tier 1) = orientación estable, NUNCA números en vivo.** Nada refresca MEMORY.md (checkpoint/audit solo lo leen para confirmar que el sistema existe; no lo carga session-start ni lo parsea recall — es doc de orientación human/agente). Por eso cualquier dato volátil ahí (conteos de corpus, rangos de fecha, "latest session: X") se queda stale en silencio (caso paperclip: "11 sessions 2026-04-06 to 2026-04-08" cuando había 293). El fix NO es instruir al agente a mantenerlo (re-crea la fragilidad de #57 + duplica lo que `/status-3t` computa on-demand) — es **no almacenar datos volátiles en Tier 1** y que `/audit-3t` detecte la deriva (warning-only, v2.9.3). Un status estable de una línea ("Plugin structure created") está bien; números/fechas que duplican los índices son el problema. Refuerza #1/#2 (Tier 1/2 coordinan, no almacenan). v2.9.3.

## External Integrations (Evaluated)

62. **GitHub Issues evaluado y descartado como storage de pendientes.** Investigación profunda (5 subagentes, v.2026-07-13): cada proyecto OSS construido específicamente para memoria de tareas de agentes IA (Beads/`bd`, Backlog.md, Task Master) eligió archivos git-nativos como fuente de verdad y usa GitHub Issues a lo sumo como import one-way o puntero cruzado — nunca como backbone. Beads lo rechaza explícitamente: sin dependency-graph semántico, sin operación offline, lock-in a GitHub (rompe portabilidad a GitLab/self-hosted/sin-remoto), rate limits, sin dedup nativo entre sesiones concurrentes. Mem0/Letta/Zep/Cognee no integran Issues. El caso donde Issues sí funciona (Copilot coding agent, Claude Code Action) es delegación de una tarea puntual a un agente — problema distinto a memoria persistente entre sesiones. Riesgo adicional si se agregara un loop autónomo: inyección de prompt vía contenido no confiable (incidente real 2026 "hackerbot-claw"), spam, necesidad de safe-outputs/GitHub App tokens/idempotencia. Decisión: pendientes se queda 100% en archivos git-versionados. Único valor legítimo identificado: un exportador opcional, opt-in, one-way (local→GitHub, campo puntero `_gh:` nunca autoritativo) — diseñado pero NO construido, ver [[research/github-issues-vs-pendientes]].

## Cross-Platform Configuration

63. **`export VAR=val` no aplica en Windows nativo — depende de la shell.** Al recomendar `THREET_CONTEXT_WINDOW`/`DISABLE_AUTO_COMPACT` (o cualquier env var del plugin) a un usuario Windows, la sintaxis correcta varía: PowerShell usa `[Environment]::SetEnvironmentVariable("VAR","val","User")` para persistente o `$env:VAR="val"` para sesión; cmd.exe usa `setx VAR val` (no afecta la consola actual, requiere una nueva); Git Bash/WSL sí usa `export` pero en `~/.bashrc`/`~/.bash_profile`, no `~/.zshrc`. Un agente que solo conoce bash/zsh debe detectar la shell del usuario antes de dar el comando, no asumir sintaxis Unix. v2.10.0+ (documentado 2026-07-22).

## Fallos silenciosos (v2.11.0, 2026-08-18)

64. **Un componente que descarta y DESPUES cuenta imprime un total falso, y eso es indistinguible de "no hay nada".** El parser de `_pendientes.md` solo reconocia `## Alta/Media/Baja`; cualquier otro header ponia `current = None` y sus items se perdian, pero `total` se calculaba sobre lo que quedo. Resultado medido en 12 proyectos: `unifi-expert` inyectaba **0 de 15** pendientes durante meses, Vecinex 1/11, Will-Ops 86/109, paperclip 540/546. Nadie lo noto porque un bloque vacio se ve igual que un proyecto sin pendientes. La leccion no es "faltaba un header": es que **nadie comparaba nunca el output del hook contra el archivo**. Defensa generica, no puntual: el componente audita su propio parseo y REPORTA lo que excluye —secciones fuera de esquema, encabezados duplicados, items bajo secciones cerradas, desajustes de conteo— aunque no tenga nada que inyectar (el auto-chequeo debe correr ANTES de cualquier `exit` por "total == 0", que es justo el caso de supresion total).

65. **Clasificar por prefijo se traga secciones vivas; anclar el match.** Al arreglar (64) se introdujo `low.startswith(("## scope", "## notas", ...))`: `## Scope expansion tasks` y `## Notas pendientes` —secciones perfectamente vivas— desaparecian enteras Y sus items se restaban del auto-chequeo, o sea el mismo fallo silencioso por otra puerta. Igual de peligroso: detectar frontmatter con "cualquier `---`" hace que una regla horizontal a media pagina suprima el resto del archivo. Reglas: match anclado al final con sufijo acotado (parentesis o fecha), y frontmatter solo si el `---` es la primera linea no vacia.

66. **Un arnes de pruebas puede consumir no-evidencia, y entonces vigila nada.** Dos veces en la misma sesion: (a) el helper mezclaba stderr en stdout y trataba "salida no vacia" como exito, asi que un traceback hacia PASAR los casos positivos; (b) los fixtures se escribian con `printf`, y cualquier comando con comillas producia un `settings.local.json` invalido — el detector no leia nada y el caso NEGATIVO pasaba en verde por un fixture roto. Reglas para cualquier arnes: stderr separado, exigir exit 0 **y** stderr vacio antes de mirar el patron, exigir el marcador literal (no "hubo salida"), validar que el fixture sea valido antes de concluir, y **comprobar que el arnes falla cuando el componente se sabotea** — si no falla, no prueba nada.

67. **La deteccion que vive en un comando opt-in no llega a nadie.** `/migrate` y `/audit-3t` ya detectaban el hook local duplicado, pero son comandos que se corren una vez al adoptar el plugin y nunca mas: ocho instalaciones pagaron el corpus dos veces (crudo + curado, hasta 34 KB por sesion) durante meses. Peor, `/migrate` se abstenia explicitamente en el unico caso que de verdad duplica ("Found existing custom hook — not removing. Verify this is intentional"), o sea que a quien lo corrio le dijo que estaba bien. **La unica superficie que alcanza a cada instalacion en cada sesion sin que nadie pida nada es el hook SessionStart** — ahi pertenece la deteccion; el comando opt-in se queda con la correccion consentida.

Pero los proyectos armados con esa receta arrastran el hook al copiarse el scaffold de uno a otro (los 7 de `sms-masivos` datan de "Initial commit — migrated from Dedicated", 2026-04-01/02). Al afirmar un origen, buscar en la historia COMPLETA incluyendo rutas borradas (`git log --all -S'<ruta>'` sobre todo el repo, no solo sobre `plugins/`).

69. **Detectar "que ejecuta un comando" no es buscar la ruta en el texto.** El detector de (67) paso por cuatro rondas de correccion: `$CLAUDE_PROJECT_DIR` vs `${CLAUDE_PROJECT_DIR}`; mirar solo el primer `.sh` (un huerfano al principio tapaba al real); reportar rutas solo MENCIONADAS (`echo "…/session-start.sh"`); `builtin bash x.sh`, que no ejecuta nada; y `bash -c "echo x.sh"`, cuyo argumento es un programa, no una ruta. Lo que funciona: trocear con `shlex` (respeta comillas), saltar prefijos transparentes (`exec`/`nohup`/`command`/`time`/asignaciones `VAR=`), exigir posicion de ejecucion (primer token del segmento, o posterior detras de un interprete), y seguir `-c` recursivamente **solo si quien lo recibe es una shell**. Declarado fuera de alcance: backticks, `$()`, heredocs y `eval`.

## Ambito de instalacion y pruebas del hook (v2.11.1, 2026-08-18)

70. **`$CLAUDE_PROJECT_DIR/.claude/commands` ES `~/.claude/commands` cuando la sesion se abre desde `$HOME`** — o sea el ambito USER, global, no el del proyecto. El plugin dejaba ahi una copia de cada comando `-3t`, y desde ese momento el usuario ve `/checkpoint-3t` DUPLICADO (user + project) en todos sus proyectos, **permanente y sin ninguna pista de su origen**; peor, la copia global se queda vieja porque el auto-update solo toca las locales (4 de 7 ya diferian de las plantillas tras un mes). Condiciones: que exista memoria para `$HOME` (Model B en `~/memory/` o auto-memory en `~/.claude/projects/-Users-<user>/memory/` — con eso el hook no sale temprano) y abrir una sesion desde `~`, que es justo lo que hace quien prueba el plugin sin entrar a un proyecto. **Son tres rutas**: el hook SessionStart y ademas `/setup-memory` y `/migrate`, que escriben ahi directamente y producen el duplicado en el acto. Regla general: antes de escribir en `$CLAUDE_PROJECT_DIR/.claude/`, comprobar que no sea `$HOME` — ese directorio tiene semantica global.

71. **`bin/resolve-project-dir.sh` hace `_HOOK_INPUT=$(cat)` y BLOQUEA si se le invoca sin stdin.** No afecta a Claude Code, que siempre le pasa el JSON del hook, pero cuelga cualquier invocacion manual: toda prueba del hook necesita `< /dev/null`. Costo real: dos diagnosticos falsos en la misma sesion —el cuelgue se atribuyo primero a "artefacto de la primera invocacion" y despues casi a la guarda recien escrita— antes de mirar el `cat`. Cuando un script se cuelga sin salida, sospechar de una lectura de stdin antes que de la logica que acabas de tocar.

72. **Probar el hook contra proyectos reales los MUTA.** `session-start.sh` instala y actualiza los comandos `-3t` en el `CLAUDE_PROJECT_DIR` que se le pase, asi que un barrido de verificacion sobre N proyectos les escribe archivos. En una sesion de pruebas quedaron 6 comandos nuevos en Vecinex y 3 en time-tracker (en los otros 5 solo se actualizaron los existentes, que es lo que habria hecho una sesion normal). Para verificar, usar directorios fixture; si hay que correrlo contra proyectos reales, registrarlo y revisarlo despues.

## Amend auto-referencial (v2.11.2, 2026-08-18)

73. **Un hash no puede contener su propio hash — el amend auto-referencial no converge.** `/checkpoint-3t` Step 6c pedia grabar el hash `H1` del commit recien creado en el session log y luego `git commit --amend --no-edit` para "incluirlo" en ese mismo commit; escribir `H1` en un archivo trackeado cambia el arbol y produce `H2 ≠ H1`, asi que el hash grabado queda obsoleto en el instante en que se graba — es un punto fijo que no existe para un hash criptografico. En sesiones reales esto producia tres fallos, ninguno correcto: loop de re-amend intentando que coincida, abandono silencioso, o un falso "listo" — los tres dejan el hash apuntando a un commit huerfano, peor que no grabarlo. Cualquier instruccion con la forma "graba X del commit Y dentro del commit Y" tiene el mismo defecto estructural. Fix: eliminar el amend; grabar el hash como forward-reference sin comitear, se resuelve solo en el commit del siguiente checkpoint — el mismo patron que el template ya usaba para el snippet `## Como retomar` de Step 8. Reportado en issue [#8](https://github.com/vzert/3-tier-memory/issues/8).

74. **El fix de un template no llega a las copias ya congeladas — ni siquiera a la de este mismo repo.** `.claude/commands/checkpoint-3t.md` (gitignoreado) es la copia que ESTE proyecto ejecuta de verdad al dogfoodear `/checkpoint-3t`; arreglar solo `plugins/3-tier-memory/templates/checkpoint-3t.md` no la toca, porque el repo del plugin no se auto-actualiza a si mismo. Todo fix de template necesita dos pasos: la fuente (para instalaciones nuevas/con auto-update) y, si este mismo repo tiene una copia local instalada, tambien esa copia — igual que las demas instalaciones congeladas (paperclip, Will-Ops, Vecinex, etc.) que ya se rastrean en pendientes tras cada fix de template. Ver tambien #70 (mismo patron: "copia congelada no se entera sola").

75. **`find -iname` puede fallar en silencio bajo el proxy `rtk`.** `find <dir> -iname "archivo.md"` no encontro una copia que si existia y que `grep -rn` si encontro segundos despues — sin mensaje de error, solo un resultado incompleto. Causa probable: el shim de `rtk` sobre `find` no soporta todas las formas de invocacion y filtra en silencio (confirmado que rechaza predicados compuestos como `-o`/`-not` con un error explicito, pero el caso simple de `-iname` fallo sin avisar). Regla: para confirmar la AUSENCIA de un archivo (no solo su presencia), usar `grep -rn` como respaldo antes de concluir "no existe".
76. **Claude Code no impide perder cambios ajenos en un archivo compartido — solo avisa.** Verificado 2026-09-02: `Read` → otro proceso inserta una línea → `Edit` con ancla que aún coincide se aplica con un aviso; luego `Write` con la copia vieja se aplica sin error y borra las líneas ajenas. Un lock alrededor de la escritura (el intento previo con `mkdir`) hace atómico el byte, no la decisión: dos agentes reconciliando pendientes o numerando la regla siguiente chocan igual. La comunidad que funciona (Basic Memory, claude-remember, Letta, Backlog.md) escribe lo concurrente append-only y deja que un solo compactador proyecte al markdown; donde SQLite es la verdad aparecen corrupciones (claude-mem) o hay que pasar a servidor (Beads). Diseño adoptado: [[plans/plan-journal-concurrencia-v2.12.0]], investigación en [[research/concurrent-memory-writes]].

77. **Los pendientes ya no se escriben a mano: `journal-emit.py` + `journal-compact.py` (v2.12.0, Fase 1).** Cada `pendiente.add`/`pendiente.resolve` es un archivo JSON en `memory/.journal/pending/` creado con `O_EXCL`; el compactador único lo aplica bajo lock `mkdir` con TTL 60 s como delta anclado (insertar bajo header, borrar por id, llenar celda por id). La identidad de un pendiente es `_id: p-<sha1 10 hex>_` de (texto normalizado + creado + origen): dos agentes que extraen el mismo pendiente el mismo día producen el mismo id y se escribe una vez. Consumidores del sufijo `_id` que deben ocultarlo: parser de `session-start.sh`, `build-recall-index.py`, `enrich-memory.py` (lo asigna con `--only creado,id`). Quien lee `- [ ]` y muestra texto debe quitar `_id` igual que quita `_origen`/`_creado`. Prueba de aceptación: `bin/test-journal-race.sh` (falla si el compactador no hace nada: control negativo verificado). Sesiones/reglas/planes siguen a mano hasta Fase 2. Ver [[plans/plan-journal-concurrencia-v2.12.0]].
78. **Un lock `mkdir` sin marcador no está vencido: hay una ventana real entre `mkdir` y escribir `acquired_at`.** Tratar "marcador ausente" como "huérfano" hizo que 2-3 procesos robaran un lock vivo en 1 de 4 corridas de la prueba de carrera. Fix en `journal-compact.py`: los marcadores se escriben a tmp + `os.replace` (nunca se lee uno a medias) y, si falta, cuenta la mtime del directorio, que existe desde el `mkdir`. El steal gate (segundo `mkdir` + re-verificar TTL dentro) sigue siendo necesario; solo no basta. `lock-tier2-write.sh` (el hook previo, sin cablear) tiene la misma ventana y se conserva solo como referencia.

"¿sigue siendo un compromiso?" se contesta con la fecha. Pero la edad **tampoco** discrimina si el backlog es trabajo real sin priorizar: a N=90, 29 de 30 candidatos leidos seguian vivos. Solo sirve la ventana que el propio item declaro, y esa solo existe hacia adelante.
109. **Escribe el destino antes de borrar el origen.** `apply_expire_index` borraba la linea de `_pendientes.md` y confirmaba antes de escribir `_caducados.md`: un fallo entre las dos escrituras perdia la unica copia. El peor caso de un traspaso debe ser "esta en los dos" — visible y reparable — nunca "en ninguno". Y el test tiene que **inyectar el fallo** (destino inescribible), no mirar solo el estado final feliz.
110. **Un cursor de paginacion tiene que ser una clave estable, no una posicion.** Con `--offset` numerico, cerrar items de un lote acorta la lista y el siguiente se salta los que ocupan los huecos. Con solo la fecha e inclusivo, varios items del mismo dia repiten el lote para siempre. La clave correcta es `(fecha, id)` con corte estricto — ni repite ni salta — y los items sin fecha necesitan su propia clave para ser alcanzables.
111. **Una verificacion que solo existe en la conversacion no existe.** Afirme "6 de 6 positivos verificados a mano" y el verificador externo lo marco como infundado: no habia fichero que re-derivar. Lo mismo con la sensibilidad de un instrumento medida sobrescribiendo su salida original — la comparacion deja de ser reproducible. Congelar cada variante como fichero propio, corridas en el mismo momento sobre el mismo corpus.
112. **Un umbral por conteo dispara en el proyecto mas sano.** Medido 2026-09-11: paperclip tiene 576 pendientes abiertos y el **mejor** ratio de cierre (0.76 en 30 dias); Will-Ops tiene 91 y cierra 0.00. Un aviso de "tienes demasiados pendientes" por numero absoluto seria papel tapiz en 3 de 5 proyectos y se equivocaria de diana. La senal es **cierra/entra por ventana**, no el tamano de la lista.
113. **Una clave de cursor "estable" tiene que serlo entre pasadas, no solo dentro de una.** La regla 110 pedia que los items sin fecha tuvieran "su propia clave": se les dio un contador por POSICION. Es unico dentro de una pasada y cambia en la siguiente — al cerrar un item anterior, el segundo pasaba de `sin-id-0002` a `sin-id-0001`, el corte estricto daba falso sobre su propio cursor y ese item no volvia a salir nunca. La clave de un item tiene que salir del ITEM (hash de su texto), no de que haya a su alrededor. Y validar solo la FORMA del id deja pasar un id inventado, que se traga en silencio todo lo de esa fecha con id menor: como no se puede exigir que el id siga abierto (cerrarlo es justo lo que hace el barrido), se le puso al cursor un digito de control. **Ese digito NO da procedencia** y la ronda 5 lo rompio fabricando `2026-01-01:p-deadbeef00:8ae6` — id inventado, digito bien calculado, exit 0: es una sha1 publica del propio id, asi que solo detecta una cadena manglada. Lo unico que da procedencia es que el item tenga `_id` **persistente**, y eso ya existia sin usarse: una pasada de `enrich-memory.py --apply` le puso id a 125 de 125 items en seis corpus reales (medido sobre copias, 2026-09-11). La leccion de segundo orden: antes de inventar una identidad sintetica, mira si tu propio sistema ya sabe persistir la de verdad.
114. **Revisar los llamantes de una funcion no prueba que sea la unica.** La ronda 4 del adversario persiguio el contrato de salto de linea mirando los ~25 llamantes de `atomic_write` en journal-compact.py, los declaro limpios y refuto el ataque. Habia SEIS rutas de escritura en `bin/`, cada una con su propia copia del patron, y tres seguian en modo texto — incluida la de un redactor de secretos cuyo docstring afirmaba "body is otherwise byte-identical". La pregunta correcta no es "¿quien llama a esta funcion?" sino "¿cuantas implementaciones de esto hay?". Y el arreglo no es revisarlas: es una prueba que ENUMERA las escrituras del codigo y exige la garantia en todas, porque una septima copia no la va a buscar nadie. Corolario medido el mismo dia: `newline=""` en la escritura no basta si la lectura es universal — para entonces el `\\r` ya no esta, y hay que mirar el fichero en binario.
115. **"Eso solo pasa en Windows" es una premisa que hay que medir, no asumir.** El contrato de saltos de linea se publico razonando que un fichero CRLF solo aparece en un checkout de Windows, asi que el riesgo en macOS era teorico. Falso: Will-Ops, en macOS, tiene 10 ficheros .md en CRLF **puro** (lineas == CR), llegados por Syncthing desde otra maquina. Medido sobre copias el 2026-09-11: la version anterior convertia esos diez ENTEROS a LF en cada pasada del enriquecedor (981 CR -> 526), y nadie lo habia notado porque el modo de fallo es un diff gigante en un fichero que nadie diffea. La forma de comprobarlo no es leer el codigo: es correr las DOS versiones sobre copias del corpus real y contar bytes. Un contrafactual medido convierte "no observe corrupcion" en "esta es la corrupcion que el arreglo evita".
116. **Un enlace de Tier 2 a un Tier 3 que aun no existe es una violacion del dual-write, y el emisor callaba.** El orden de /checkpoint-3t es Step 2 (escribir el session file) y DESPUES Step 3 (emitir los pendientes). Emitir a media sesion invierte ese orden: el indice apunta a un fichero que nadie escribira si el checkpoint no llega. Paso cinco veces en una sesion, con DOS slugs inventados distintos, y los enlaces rotos mas viejos del repo son de PLANES con el mismo fallo. `check-wikilinks.py` lo detectaba desde siempre y `/audit-3t` ya lo corre: **lo que faltaba no era el detector, era avisar en el momento de crear el enlace** en vez de en una auditoria posterior que nadie corre a tiempo. Y lo encontro otro agente leyendo el indice, no una prueba — el detector existia y nadie lo habia mirado.
117. **Un parametro que el applier acepta y no aplica es un campo sin lector, y el indice miente en silencio.** `apply_plan_upsert` actualizaba estado, sesion, pendientes y learnings de una fila existente, pero nunca la celda 0: `--title` se aceptaba y se descartaba. El indice conservo durante dias el titulo con el que nacio el plan —nombrando dos mecanismos ya descartados— mientras el fichero decia lo contrario. Al anadir un parametro a un emisor, comprobar que el applier lo lee **en los dos caminos**: alta y actualizacion.
118. **Si el camino por defecto no esta cubierto, el guard no es opcional: es decorativo.** `journal_strict` es un PreToolUse sobre `Edit|Write|MultiEdit` y Bash no esta en su matcher; ademas una sesion en modo auto tiene instruccion explicita de preferir Bash sobre Edit/Write, asi que ahi el guard no se salta a veces — se salta SIEMPRE, por construccion. Medido 2026-09-11: 96 escrituras por Bash a un indice protegido desde que el journal es obligatorio, en 9 proyectos; cruzando con `.journal/applied/`, 43 ids de Tier 2 sin NINGUN evento que los emitiera. Y el dato que invierte la conclusion facil: el unico proyecto con el guard ENCENDIDO es el que mas ids escritos a mano acumula (25 de los 43) — no porque se porten peor, sino porque es el unico donde el agente se entera y lo dice. Encender el guard no lo arregla; lo que llega a todos es una deteccion que no lea `.memory-config`.
119. **Un falso positivo al BLOQUEAR cuesta trabajo bueno; al AVISAR cuesta una linea de texto.** Esa asimetria decide si te puedes permitir un detector aproximado. Descarte parsear Bash porque para DENEGAR es adivinar — correcto — y con ello tire el eje entero, en vez de ver que la version debil de esa misma accion tiene otro coste. Regla general para un modal: **por cada opcion que descartaste al redactarlo, comprueba si su version mas DEBIL esta en el menu** (bloquear->avisar, borrar->archivar, fallar->reportar). Victor tuvo que pedir el aviso en Bash por su cuenta y el adversario lo conto como violacion de autonomia: la decision se le asigno, pero su respuesta no estaba entre las opciones.
120. **Sincronizar mejor no cierra una ventana contra quien no pide el lock.** Tres intentos sobre el mismo defecto: "--check-drift no toma el lock" -> tomarlo; "lo parti en dos locks" -> fundirlos. Ninguno era el problema, porque una escritura por Bash —el caso exacto que el mecanismo existe para cazar— nunca pide `.journal/.lock`. La ventana real estaba entre las DOS LECTURAS DE BYTES: la de comparar y la de sellar. Se cierra reusando UNA lectura, no sincronizando. Antes de arreglar una carrera, pregunta si el escritor que te preocupa respeta el lock; si no lo respeta, el lock no es la variable.
121. **Un detector que decide a quien mirar puede perderse justo al que importa.** `check-index-writers.py` solo escaneaba los scripts que NOMBRAN un indice como literal — y `scan-secrets.py`, que recorre todo `memory/` con `os.walk` y reescribe `_pendientes.md` cuando encuentra un secreto, construye la ruta dinamicamente: no aparecia ni en la lista de escritores ni en la de exentos. Era invisible al detector instalado para "dejar de adivinar". Cuatro versiones de deteccion por analisis de texto salieron cortas antes de aceptar la unica forma que no puede perderse nada: **no decidir a quien mirar** — que TODOS declaren, y exigir la declaracion. Un falso positivo cuesta una linea de comentario; el hueco costaba una acusacion falsa a una herramienta del propio plugin.
122. **Un test que muta un fichero versionado lo deja roto cuando aborta.** Para probar que una asercion discrimina, mutaba `enrich-memory.py` en su sitio y lo restauraba despues; con `set -e`, un fallo intermedio corto el script antes del restore y dejo el fichero del ARBOL DE TRABAJO corrupto — el fallo se propago a otras aserciones y parecia otro bug. Un test trabaja sobre una COPIA (`cp -R bin/ $T/bin` y se le pasa el directorio), nunca sobre el arbol. Corolario del mismo dia: `git stash push` sobre un fichero limpio no crea stash, asi que una prueba de discriminacion montada sobre stash pasa sin probar nada.
123. **Un tope de tiempo sobre la lectura ENTERA de stdin trunca; solo debe acotar la espera del PRIMER byte.** Medido con un productor que manda 300 bytes, para 4 s y manda el resto, tope en 2 s: `read -r -d '' -t 2` deja 0 bytes y rompe la tuberia del escritor; `read -r -d '' -n 1 -t 2` + `$(cat)` entrega los 619. Y el `cat` va DENTRO del `if`: llamarlo tras un tope agotado se cuelga igual que antes.
124. **Antes de culpar a un builtin por lento, saca tu propio codigo del camino y vuelve a medir.** Atribui '118 s con 1 MB' a que `read` va byte a byte y estuvo a punto de entrar en el CHANGELOG como hecho. Era un bucle propio de recorte de saltos que copiaba 1 MB por vuelta; `read -r -d ''` pasa 5 MB en 1-2 s.
125. **Un pty con `script` no prueba que algo se cuelga sin stdin: `script` cierra el pty al terminar y manda EOF.** Medido: con solo el otro defecto arreglado, ese caso PASA contra el codigo que si se colgaba. El discriminador portable es un fifo que nadie escribe, abierto con `exec 9<>fifo` (`9>` bloquea hasta que haya lector). Y `script` hereda el stdin del llamante: sin `</dev/null` la deteccion sale distinta segun quien corra la suite.
126. **Una cifra de discriminacion que depende de la maquina no es evidencia, aunque reproduzca 3/3 en la tuya.** Afirme `pass=18 fail=2` contra una variante descartada; el adversario midio 19/1 en otra maquina. Afirma solo la asercion cuyo resultado no depende del entorno, y di cual es.
127. **Una funcion de test entubada corre en un subshell y sus variables no vuelven al padre.** `printf ... | probe` dejo OUT y RC sin asignar y la suite murio con `RC: unbound variable`. Pasa el stdin por REDIRECCION (`probe < fichero`), nunca por tuberia, cuando la funcion tiene que devolver estado.
128. **Al arreglar un defecto, barre TODOS los ficheros que lo afirman, no solo el que recordabas.** Corregi el comentario de `triage-3t.md` y dos verificadores independientes encontraron, cada uno por su lado, el MISMO texto exacto vivo en `triage-scan.py` y `expire-pendientes.py`. Un `grep` de la frase, no de la memoria.
129. **El `grep` de una sesion de Claude Code no es `/usr/bin/grep`.** Es una funcion de shell que instala el snapshot de la sesion y que ejecuta el ugrep incluido con `--ignore-files`, o sea que **salta lo que esta en `.gitignore` al recursar desde la raiz**. Medido en este repo 2026-09-11: `grep -rl "## Cambios realizados" .` devuelve 4 ficheros; `/usr/bin/grep -rl` sobre lo mismo devuelve 50, incluidos todos los de `.claude/`, `memory/` y `.goalspec/`. Nombrar el directorio de forma explicita si lo encuentra — el punto ciego es solo al recursar. Ya costo dos veces: un falso positivo del verificador externo en 2.15.0 ("el comando local sigue desactualizado" sobre un fichero sincronizado) y un barrido de superficie incompleto en 2.15.1. **`grep -r` sin resultados no es prueba de ausencia en un repo con `.gitignore`.**
130. **Un barrido de superficie se hace enumerando directorios, no buscando patrones.** En 2.15.1 se busco el esqueleto de session file en `templates/` y `.claude/commands/` y se concluyo "exactamente dos constructores". Existia un tercero en `plugins/3-tier-memory/commands/`, la superficie NATIVA del plugin, obsoleto desde el 2026-09-02 y sin el campo que esa misma version decia arreglar: el defecto seguia vivo en una de las dos vias de invocacion. Conocer dos instancias de algo crea la conviccion de que son todas. Enumera los directorios candidatos primero (`ls`/`find`), y solo despues busca patrones dentro.
131. **No cites la salida de un instrumento sin mirar como la calcula.** Se publico "10 sesiones sin procesar" en un CHANGELOG copiandolo del aviso del hook de arranque. Ese contador hace `JSONL_COUNT - len(processed) - 1` e **ignora `skipped[]`** (17 entradas en esta instalacion) ademas de contar un UUID que ya no existe en disco — es un defecto conocido (`p-6ebc35ab3d`), no un dato. Lo encontro el verificador externo. Cuando el instrumento no es de fiar y no hay tiempo de arreglarlo, **quita la cifra**: no la sustituyas por otra que tampoco puedas re-derivar.
132. **Un control que no discrimina puede ser el parametro, no el mecanismo.** Probando que `expire-pendientes.py` respeta la ventana `_revisar`, el control con `--modo edad --days 1` dio `candidatos: 0` con y sin ventana, y se publico como "no demostrado". El item tenia `edad=1 <= days=1`, asi que no era candidato por ninguna via: la prueba no podia separar las ramas. Con `--days 0` si discrimina — `candidatos: 1` sin ventana, `candidatos: 0` + `excluidos: _revisar futuro 1` con ella. Antes de declarar que un mecanismo no se puede demostrar, comprueba que el caso de prueba **cae dentro** del rango que el mecanismo evalua.
